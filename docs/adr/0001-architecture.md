# ADR 0001: ядро на Python вместо Bash

- Статус: принято
- Дата: 2026-11-02
- Основание: [ревью 2026-11](../review-2026-11.md)

## Контекст

Ревью `main` @ `33f2d51` показало три группы проблем.

1. Режим по умолчанию не был read-only: запуск setup Mail-in-a-Box (R-01), импорт
   Python-модулей из текущего каталога от root (R-02), `sendmail -bv` (R-21), `rpm -Va`
   со скриптами пакетов (R-22). Позиции R-01…R-22 точечно исправлены в Bash (#7, #8),
   чтобы рабочая версия была безопасной до выхода новой.
2. Результат нечестный: нет данных, нет прав или утилиты дают OK или FAIL (R-04, R-05,
   R-08, R-23, R-27, R-29). Модели статусов UNKNOWN и N/A нет.
3. Около 1000 строк проверок выполняются на верхнем уровне скрипта и вызывают внешние
   команды напрямую с фиксированным PATH. Протестировать проверку можно только на
   настоящей системе или с поддельными бинарниками в системных каталогах (ревью, раздел 6).

Требования задания: один runner с allowlist argv, timeout и лимитом вывода; подмена runner
в тестах; fixtures и end-to-end сценарии для каждого стека; UNKNOWN и N/A; стабильные ID;
каталоги ru/en; mypy --strict и ruff; совместимость CLI, кодов возврата и JSON.

## Варианты

### A. Рефакторинг Bash

Функция на проверку, единая обёртка `run` с allowlist, bats-core, fake-режим.

- Плюс: нет новой обязательной зависимости, небольшой diff.
- Минус: в Bash нет структур данных. Finding с Evidence и Completeness пришлось бы гонять
  через TSV, как сейчас.
- Минус: fake-режим для тестов означает переменную окружения или файл, который меняет
  поведение root-скрипта. Это новая поверхность атаки. Альтернатива, поддельные бинарники,
  требует root или контейнер на каждый тест.
- Минус: проверка argv по таблице, разбор журналов, часовые пояса и JSON в Bash
  выполняются через внешние утилиты (GNU date, gawk, python3). Это те же зависимости,
  только неявные.
- Минус: mypy --strict и ruff к Bash не применимы. Требование CI выполнить нельзя.

### B. Гибрид: Bash-оркестратор и Python-модули

Это текущее состояние: Bash вызывает Python для статистики и JSON.

- Минус: два языка и обмен через временные файлы. Тестируемость оркестратора не меняется,
  и именно в нём находятся R-04…R-12.

### C. Python 3.9+, только стандартная библиотека

Пакет `mail_sec_audit/` со структурой из задания, поставка через zipapp, совместимый запуск
`sudo bash mail-sec-audit.sh`.

- Плюс: argv без shell, таймауты и лимиты вывода в одном месте (`runner.py`), потоковое
  чтение журналов и `.gz`, `datetime` и `zoneinfo`, `json`, `ipaddress`, `ssl`.
- Плюс: в тестах runner и файловая система подменяются, сценарии стеков выполняются без root.
- Плюс: mypy --strict и ruff проверяют весь код.
- Минус: Python 3.9+ становится обязательным. Раньше он требовался только для статистики и JSON.

## Решение

Вариант C. Старый скрипт используется как список требований. Построчный перевод не делается.
Каждая проверка получает новую реализацию или обоснованное удаление,
см. [таблицу соответствия](../check-mapping.md).

## Контракты

### CLI

Все флаги 2.3 сохраняются с теми же ограничениями и кодом 64:
`--days`, `--mail-top`, `--from`, `--to`, `--hostname`, `--domain`, `--dkim-selector`,
`--platform`, `--format`, `--redact`, `--deep`, `--report`, `--append-report`,
`--interactive`/`--manage-bans`, `--verbose`, `--no-color`, `--version`, `-h`/`--help`,
переменная `MAIL_AUDIT_ALLOWED_PORTS`.

Добавлены:
- `--lang ru|en`; без флага язык берётся из `LC_ALL`, `LC_MESSAGES`, `LANG`;
- `--format json-v1` (документ 2.3), см. раздел JSON.

`sudo bash mail-sec-audit.sh` остаётся основным способом запуска. Скрипт превращается в
обёртку, которая проверяет Python ≥ 3.9 и запускает пакет в изолированном режиме (`-I`).
Дополнительно доступен один файл `mail-sec-audit.pyz`.

### Коды возврата

| Код | Значение |
|---:|---|
| 0 | нет WARN, FAIL и UNKNOWN |
| 1 | есть WARN или UNKNOWN, FAIL нет |
| 2 | есть FAIL |
| 64 | ошибка аргументов |
| 69 | нет подходящего Python (раньше: нет python3 для `--format json`) |
| 73 | не удалось безопасно создать или дописать отчёт |
| 75 | уже работает другой экземпляр (новое: блокировка параллельного запуска) |
| 129, 130, 143 | остановлен сигналом HUP, INT, TERM |

Отдельный код 3 для UNKNOWN не вводится. UNKNOWN означает, что результат нужно проверить
вручную, поэтому он даёт 1, как WARN. Коды 69 и 73 существовали и раньше, но не были
описаны. Код 75 новый, его значение взято из sysexits (EX_TEMPFAIL), как у 64, 69 и 73.

### JSON

FleetOps (`fleetops/domain/models.py`) объявляет `HealthResult` и `CheckResult` с
`extra="forbid"` и принимает только `schema_version == "1.0"`. Документ, который сохраняет
поля v1 (`tool`, `target`, `findings`, `mail_statistics`, …), валидацию FleetOps не пройдёт.
Документ в формате HealthResult ломает совместимость с текущими потребителями `--format json`.

Решение владельца (2 ноября 2026, при выпуске 3.0.0):
- `--format json` выдаёт HealthResult: `schema_version "1.0"`, `host{id,hostname}`,
  `collected_at`, `duration_ms`, `overall_status`, `checks[]`. Каждый finding становится
  CheckResult, детали (исходный статус, секция, источник, доказательство, шаг) лежат в
  `metrics`; версия, период и пробы — в проверке `CTX.AUDIT`, статистика Postfix — в
  `FLOW.STATISTICS`, файловые системы — в `DISK.FILESYSTEMS`. Совместимость проверяется
  контрактными тестами по полям FleetOps;
- `--format json-v1` сохраняет документ 2.3 (`schema_version: 1`) с прежними полями и
  значениями `severity`/`result.status`, новые поля только добавлены. UNKNOWN отображается
  в `severity: warning`, N/A в `severity: info`, точный статус в `status`;
- значения `findings[].id` — стабильные имена (`SSH.X11_FORWARDING`) вместо позиционных
  `SSH-004`, которые не были стабильными (R-07).

### Статусы

`OK`, `INFO`, `WARN`, `FAIL`, `UNKNOWN` (причина обязательна: `missing_tool`,
`permission_denied`, `timeout`, `truncated`, `no_data`, `command_failed`, `parse_error`,
`internal_error`), `N/A` (причина обязательна). Сбой проверки даёт UNKNOWN с
`internal_error`, отчёт продолжается.

## Безопасность

- `runner.py`: таблица разрешённых argv. Каждая запись содержит программу, шаблон аргументов,
  timeout, лимит вывода и обоснование отсутствия побочных эффектов. Запуск только списком argv,
  без shell. Окружение дочерних процессов: фиксированный PATH, `LC_ALL=C`, stdin из `/dev/null`.
- Явный запрет с любыми аргументами: `mailinabox`, `update.sh` и любые пути к ним.
- `docker` только `ps`, `inspect` с фиксированными шаблонами `--format`, `logs` и `exec`
  без `-i`/`-t`/`-u`/`-e`/`--privileged`. Внутренняя команда `exec` проверяется по той же
  таблице, в контейнере разрешены только записи с отметкой `container`.
- Изменяющие записи (`fail2ban-client set … banip/unbanip`, `fail2ban-client unban`, `logger`)
  отмечены `mutating`. Runner исполняет их только в интерактивной сессии после подтверждения.
- Секреты не читаются: `mailcow.conf`, `sasl_passwd`, private keys, тела писем. Хеши
  `/etc/shadow` тоже не читаются, пустые пароли определяются через `passwd -S`.
  `doveconf` вызывается только с явным списком параметров и никогда с `-x`.
- Отчёт открывается через `O_CREAT|O_EXCL|O_NOFOLLOW` с правами 0600, запись идёт через
  этот же fd. Для дописывания: `O_APPEND|O_NOFOLLOW`, обычный файл, владелец euid,
  `st_nlink == 1`, нет записи для группы и других.
- Блокировка `fcntl.flock` на `/run/mail-sec-audit.lock` (root) или в `XDG_RUNTIME_DIR`.
- Сетевые пробы: TLS только к локальным адресам listener'ов, каждая проба перечисляется
  в `completeness.probes`. DNS только при явном `--domain`.
- Значения из журналов, DNS и сертификатов недоверенные. В терминале управляющие символы,
  ANSI и bidi-символы заменяются экранированием.

## Структура

```
mail_sec_audit/
  cli.py       разбор аргументов, без логики проверок
  app.py       блокировка, сигналы, запуск, отчёт, код возврата
  safefile.py  файл отчёта (O_EXCL|O_NOFOLLOW) и блокировка flock
  interactive.py  меню Fail2ban, единственный изменяющий режим
  runner.py    allowlist и запуск команд
  model.py     Status, Finding, Evidence, Completeness, Report
  host.py      доступ к файловой системе, часам, euid (подменяется в тестах)
  facts/       сбор, один модуль на источник
  logs/        источники, время, парсеры Postfix/Dovecot/sshd, статистика
  rules/       одна проверка на модуль
  stacks/      mailinabox, mailcow, iredmail, generic
  render/      terminal, fleetops (--format json), json_v1 (--format json-v1), redact, sanitize
  i18n/        каталоги ru и en
```

Правила не проверяют имя стека. Всё, что различается между стеками (команды Postfix и Dovecot,
источники журналов, ожидаемые порты, сервисы, путь к почте, версия), предоставляет объект стека.

## Последствия

- Хосты без Python 3.9 (CentOS/RHEL 7; RHEL 8 без пакета `python39`) не поддерживаются.
  Обёртка завершится с кодом 69 и сообщением, что нужно установить. На Ubuntu 22.04+,
  Debian 11+, RHEL 9 и Rocky 9 системного Python достаточно.
- Exim, Sendmail и OpenSMTPD сохраняют прежний уровень: определение, состояние сервиса,
  relay-эвристика и очередь. Статистика почты, как и раньше, только для Postfix.
- Общий пакет с miab-radar не создаётся. Структура совпадает, чтобы небольшие модули
  (runner, logs/time) можно было перенести позже.
